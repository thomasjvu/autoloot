## Outcome
From Packing by buyer, seller selects/reviews multiple matching paid physical orders, measures one package, obtains one Shippo quote and buys one label. Purchase persists an immutable membership and attempt before contacting provider. After explicit carrier handoff, every member order becomes shipped atomically with the same tracking. Opening Shipping from any member recovers the same package. Buyer responses retain private ownership boundaries. Existing separately agreed shipping charges and order totals stay unchanged, with this stated at creation; no automatic refunds/partial refunds. This stage is combined fulfillment, not consolidated checkout.

## Current behavior
Shipping stores snapshots under each order.shipment, commits purchase intents before provider calls, locks by order, checks test/live/payment eligibility, then record() verifies attempt metadata/rate/test. Refunds, tracking imports, reset and engine dispatch inspect those snapshots. Buyer viewer explicitly allowlists shipment fields. Never weaken these guarantees. ordersPage uses packingGroups(), grouped headers and existing order controls; app.js wires data-shipping-order into shippingOrderDialog. All API POST actions run behind common auth policy; server returns refreshed admin state.

## Design constraints and ordered implementation
1. Inspect all label/refund/import/reset guards and tests before choosing representation. Use one authoritative package shipment with explicit ID, bounded 2–50 unique member IDs, owner identity, mode, normalized complete US destination and membership snapshots. It may be a package record in engine.state or an explicit canonical leader shipment with replicated member projections; choose one and document authority. No relying on object aliasing (SQLite JSON/restarts destroy aliases). Every member must remain visibly held by the package through quote, purchasing, unknown, pending, purchased and refund-pending. Group IDs never originate from buyer APIs.
2. Creator-only create/release package actions. Validate every member belongs to SAME verified userId, mode and destination including recipient name/unit; paid eligible physical, no refund request, no active label, no existing package. Require explicit confirmation of exact membership and unchanged buyer charges. Recheck eligibility at quote and before buy after async calls; bind all membership/address snapshots to quote. Exclude different buyer IDs even with same display name, incomplete addresses, NFT, Stripe test/unverified live payments, mixed modes, duplicates, absent IDs and stale memberships. Reject malformed arrays rather than silently dropping members. Do not modify order totals or buyer shipping prices.
3. Package holds must prevent individual quote/buy/address edits/manual dispatch/CSV dispatch/refund and overlapping package creation. Release only before any purchase attempt or after provider-proven failed/voided label, with explicit confirmation and immutable history. Unknown/pending/refund-pending/purchased attempts cannot release or purchase a replacement. Retain original audit/provider evidence and old package membership/history so restart and retries never unlock uncertain spending. Existing single-order flow stays compatible.
4. Package operations (rates/buy/refresh/track/dispatch) from ANY member resolve authoritative shipment and lock ALL members consistently with single-order operations. Persist full package purchase intent and all member holds in one commit before provider spending. Quote races with individual operations or membership/address changes must be rejected/revalidated. Refresh never buys and always verifies original attempt account, metadata, rate and environment. Track reflects one shared carrier state. Persist changes on all required projections atomically.
5. Dispatch prevalidates every member including paid state, no refund, verified live money, unchanged owner/mode/destination and purchased matching label. Mark ALL members shipped in a SINGLE engine commit, never sequential orderUpdate commits; replay is idempotent only for same package/tracking and already fully shipped state. Storage failure must leave engine halted with no partial local statuses and no second purchase possibility. Individual /api/order ship and CSV tracking must not bypass package dispatch. Provider-confirmed void/refund recovers package safely; refunds on single members remain blocked until package resolved/released. Existing reset guard must see held demo package attempts, including in-flight quote calls.
6. UI: group header action to review/create package (membership and destination list, measured parcel, separately charged shipping total, explicit confirmation). Reuse Shipping dialog for shared label workflows if possible. Member rows show package membership; one package dispatch control explicitly names number of orders; from any member, show canonical package and same label. Add package release where safe. Remove obsolete 'combined labels unsupported' copy and ensure users cannot mistake grouping for auto-refunded shipping. Show useful errors and disable duplicate actions. Existing All/Attention/Packing filters keep working; package holds excluded from fresh group creation but have reachable controls.
7. Tests: meaningful domain and HTTP tests. Happy path two same-buyer orders -> one quote/transaction -> one explicit dispatch commit -> both same tracking, costs unchanged; third unselected order untouched. Mismatch/invalid membership rejection; all routes auth/privacy including other buyer and public snapshots; per-member bypass via address/refund/manual ship/CSV/individual labels blocked; overlapping concurrent creation/buy attempts and quote-time races; lost provider response + JSON roundtrip restart -> recovery through any member -> no second spending; failed/voided release + retained history; partial-invalid dispatch does not ship anyone; storage failure before intent stops spend, at dispatch no partial persistence; live/test gating. Update existing regression tests only for deliberately changed package copy/action. No live provider calls or real postage.
8. Documentation: exact create/label/dispatch/recovery/release behavior, package authority/history, API shapes, unchanged buyer shipping charges, test limits. Verify npm run check, npm test, npm run demo:check, git diff --check. Run a fixture HTTP journey covering new UI API contract. If browser QA is available, verify rendered main view/dialog and existing single order flow.
